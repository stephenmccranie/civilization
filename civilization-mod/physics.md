# Shared physical properties

## Implemented boundary

The first physical-foundation stage provides shared material data, a geometry snapshot, a read-only Sable bridge and an operator inspector. Sable continues to own motion, collisions and vessel inertia. Physical mass is now explicitly distinct from thermal capacity and existing machine work credits. This stage does **not** change live Sable mass, boat handling, cargo penalties, fuel budgets or heat-save units.

`PhysicalMaterials` loads [defaults.json](src/main/resources/data/civilization/physical_materials/defaults.json). A datapack can replace `data/civilization/physical_materials/defaults.json`, then `/reload`. The entire file is validated and swapped atomically; invalid data preserves the previous registry. Required families are air, water, wood, masonry, glass, metal, door and partial. Each defines density (kg/m³), specific heat (J/kg/K), conductivity (W/m/K), plus clearly labeled legacy heat capacity/conductance. Values must be finite, from 1e-9 through 1e9. These are initial effective game materials, not certified real-material specifications or a joule conversion for existing heat credits.

Selection: exact block ID overrides a tag; if multiple tags match, lexicographically first tag ID wins; otherwise state-aware defaults select a family. Initial exact metal mappings cover iron/copper blocks and industrial casing. Other blocks get the documented fallback rather than an inferred chemistry. Fluid blocks currently use a generic water-like physical fallback, including non-water fluids; specific fluid profiles remain work. No material/state resolution cache means reloads and tag changes cannot leave stale lookups.

`ThermalField.capacity` and `conductance` now delegate to the shared compatibility policy. Existing full/partial-block capacity, glass, doors, waterlogging and material rules remain the deployed game-tuned values. Physical kg/J/K values are visible for inspection but are not silently substituted into saved thermal energy. Legacy material-family fields remain a temporary migration boundary.

## Geometry snapshot

`PhysicalSample.at` reads the current block and cut-block contents. Full cubes, native slabs (including doubles) and mixed eighth-cells derive occupied volume, material mass, thermal capacity and six face descriptions. Vacant space adds air capacity but no rigid material mass. Solid component mass/capacity sum by eighth-volume; two halves/eight eighths conserve the original material. Mixed cells use each component's own profile.

Each face exposes solid/open area and a through-block conductive estimate. Four parallel quarter-area columns each contain two half-meter resistances in series. This respects orientation and layered resistance rather than averaging conductivity. It is a future transport input, **not yet the active heat solver**; it does not model air circulation, cross-column conduction or separate temperatures for disconnected pieces.

Other shapes use center sampling on the same eight-cell grid and are flagged approximate. Thin or decorative shapes may be underrepresented, including zero sampled occupancy. Fluid blocks are provisionally full-volume and flagged approximate. Waterlogged fluid, item inventories, tank contents and buoyant displacement are not inferred. The command explicitly says contents are excluded; an empty shell's material estimate must not be presented as fully loaded vessel mass. Snapshots are recomputed on request, not stored as a second inventory balance.

## Inspector

Operators can look at a block within eight blocks and run:

```text
/civilization physics
/civilization physics <x> <y> <z>
```

The command reports material family, occupied m³, estimated material kg, J/K capacity, current Sable mass in engine units, legacy heat values, six face contact/conductance estimates, and coordinate domain. It only inspects loaded blocks. Explicit coordinates are useful when a moving-body targeting path is ambiguous.

`SablePhysicalBridge` resolves world versus vessel UUID/plot-local position, plus transformed world center, without assuming only Civilization boats exist. Unassigned plots fail explicitly. This is a read-only address resolver: thermal state transfer through assembly, splits and unload is **not** implemented here. Moving controllers remain restricted as described in [vehicle physics](vehicle-physics.md).

## Pinned Sable proof

The actual 2.0.5 JAR's `PhysicsBlockPropertyHelper.getMass` consults solid occupancy and a block-state property. Its signature includes position but the inspected implementation does not derive inventory or mixed-block content mass. Static definitions can be generated by `SablePhysicalBridge.definition`; the GameTest-only iron definition demonstrates this using the shared metal density. Tests compare actual engine lookup with the shared value. That resource is in `src/gameTest/resources`, not the deployed mod.

Production currently observes Sable mass rather than overriding it. Dynamic per-position cut-block/cargo mass and tracker invalidation require a separate verified hook; no engine fork or hidden unsupported mutation was added. The existing live-vessel/save-reload harness need not run for this read-only/static-definition stage. Moving-address behavior still needs a live-vessel check during the next stage.

[Work order and acceptance](../open_decisions.md#unified-physical-foundation--proposed-implementation-plan) govern domain-aware thermal state, capacity/energy migration, authoritative fuel/work transactions and optional physical consequences. ## Stone cargo accounting

The first [physical storage package](../development_plan.md#physical-storage-and-increasing-scale--active-package) adds a read-only stone/cobblestone cargo audit. `CargoVolume` stores exact integer eighth-m³ units and computes whole-piece capacity without rounding up; negative and overflowing quantities fail. `StoneCargo` recognizes full Stone/Cobblestone, their native slabs and custom saw-cut halves/quarters/eighths. Two halves, four quarters or eight eighths equal one full 1 m³ block. Malformed custom material IDs remain unknown rather than using cutting's legacy fallback.

Material volume and packed storage volume are separate fields; both equal solid volume for these neatly packed construction pieces. This does not describe loose rubble or a pile packing factor. Estimated cargo mass uses the current shared material density, including datapack overrides; it is a game material estimate, not a measured rock specification. No mass/stock cache or second saved quantity is introduced.

Operators can run:

```text
/civilization cargo
/civilization cargo container <x> <y> <z>
```

The first command scans the issuing player's inventory, including hotbar, armor and offhand but not cursor-held stacks. The second scans one loaded block's direct `Container` inventory; double-chest halves are inspected separately. It refuses ungenerated loot containers rather than opening them and never loads target chunks. Bulk SavedData stores, tanks, capability-only inventories, nested contents and unsupported items need separate adapters. Reports show supported material/storage m³, estimated kg and supported/unknown occupied-stack counts. Totals are partial when unknown stacks exist; they must not be treated as complete vehicle loads.

This is an operator diagnostic, not a Survival control. Existing carrying limits, chest capacities, recipes, automation, stock, saves and live Sable mass remain unchanged. The wheelbarrow/stockpile prototype below now enforces cargo mass separately; personal/chest migration and supply-fed building remain later stages. [Design](../design_direction.md#physical-material-storage-and-handling) owns the target rules; [open decisions](../open_decisions.md#physical-storage-and-increasing-scale) owns remaining tuning.

## Wheelbarrow and material stockpile prototype

The Wheelbarrow is available in the Civilization Creative tab or `/give @s civilization:wheelbarrow`. Cargo and a Survival-craftable stockpile are implemented; wheelbarrow Survival acquisition remains pending. Place it on the top of a solid surface with enough clear space for the whole carrier. Placement checks loaded terrain, world border, collision and current claim access before consuming one item outside Creative.

Right-click the tray/front/side region to open cargo; right-click the rear/handle region to take the handles, including while holding the placement item or another item. Taking the handles does not consume the held item. The player stands behind the carrier with a pushing arm pose, rather than sitting in its tray. **W/S** push forward/backward, **A/D** turn the carrier, and **Sneak** releases. The visible model, handler position and movement use the same synchronized heading; the camera follows steering while preserving any deliberate look-around offset. Steering is applied after the player tick, retaining the previous yaw for frame interpolation in first person and both third-person views; the pushing body also interpolates its heading. Opening a screen releases the handles; cargo cannot be accessed while anyone is handling the carrier. Missing input stops drive after half a second. A parked empty carrier can be recovered with **Sneak + empty-hand right-click**. It cannot currently be broken by attacking it. Unclaimed carriers are shared; claim permissions apply to taking/recovering and are rechecked during movement. Access loss, death and entering water release the handler. Only one player can handle a carrier at once.

Forward pushing matches ordinary walking at 3.2 blocks/second; backing up uses half that speed (1.6), with 70 degrees/second turning. Leg cadence and stride use the ordinary walking animation driven by actual handle displacement, including turning, and ease to rest when blocked or idle. Handling costs the walking rate (default 0.1 kcal per horizontal block), plus the normal ascent cost (1 kcal per block gained). The server measures actual handle travel: reversing and walking around a turn cost energy; idle/blocked input does not. Warmth/work-meal discounts, shared depletion, and Creative/Spectator exemptions apply. The energy journal records `push_wheelbarrow`; its distance joins the walking counter. Cargo currently keeps this same walking-rate energy/speed; load-dependent handling remains later tuning. Native collision/gravity allow successive rises of up to one full block per step, including full-block inclines and slabs/stairs, without jumping. Taller ledges remain blocking. Each rise must leave clear space for the carrier and the standing handler; a low ceiling or denied raised footprint prevents the step. The model is 35% larger than the initial prototype: approximately 1.04 blocks wide, 2.62 long and 0.97 to the parked rear rim, with a four-degree pushing tilt. Geometry, pivots, fitted 64px/block UVs, wheel radius and handler offset scale together. Existing placed wheelbarrows adopt the correction without replacement.

The tray-and-wheel body is **solid to walking players**. Its compact yaw-dependent body box excludes the rear handle corridor, so players can approach the handles and walk away after brushing the body. A player already overlapping it can still leave. The larger whole-model envelope remains responsible for native terrain collision/stepping, clearance, claim access and rendering bounds; it is restored to the compact body after each movement query. The carrier also refuses to drive or turn its body into another player. Client interpolation updates yaw before rebuilding bounds. The player's feet follow carrier elevation on a slope; separate wheel/leg suspension and uneven-ground pose are not simulated. No jumping, buoyancy or rail requirement is added.

The server owns movement. Clients submit only bounded direction/release input, never positions or velocity. Terrain/access queries stay inside the small loaded footprint. Native entity persistence retains identity and wheel travel; pending drive input is cleared on reload. The renderer derives wheel rotation from actual horizontal displacement and smoothly lifts the handles while held, so a blocked or parked carrier does not free-spin. This is an ordinary entity, with no Sable cargo-mass or vessel integration claim.

### Cargo and transfers

Cargo uses **mass only**: the initial wheelbarrow allowance is **64,000 kg**, and a Material Stockpile holds **1,024,000 kg**. These deliberately generous game values are server-tunable through `wheelbarrowMassKg` / `stockpileMassKg` in `civilization-cargo.toml`; there is no independent stack-count, volume or material-type cap. Matching item/components merge into one long-count entry. The chest-style menu shows 27 entries per page and adds pages as needed. Exact quantities appear in tooltips, with compact counts in crowded slots. Volume is descriptive only; visible piles represent contents rather than literal packed dimensions.

Ordinary solid full building blocks, mapped native slabs and valid saw-cut pieces use their shared material density and actual full/half/quarter/eighth material volume. Tools, food, containers, block entities, TNT, unsupported shapes and malformed pieces are rejected rather than treated as weightless. The earlier stone-only inspector remains narrower than this cargo adapter. Player inventories and ordinary chests keep their existing stack limits. For example, the initial wheelbarrow fits 32 full stone blocks, 64 halves or 256 eighth pieces in one cargo entry.

Click a cargo entry to take a normal inventory stack onto the cursor; right-click takes half that normal stack. Clicking with matching cursor items deposits what fits, and right-click deposits one. Shift-click moves player inventory stacks into cargo, or fills available ordinary inventory space from one cargo entry. Cursor and player inventories always retain native bounded stack counts; oversized cargo quantities never become oversized ItemStacks. Other material types can be deposited through an empty cargo cell or Shift-click. Mass-bound partial transfers leave the remainder in the source.

Park a wheelbarrow within **three blocks** of a stockpile and open either cargo menu. **Load nearby** transfers from the other store into the opened store; **Unload nearby** transfers the opposite way. The nearby-store label identifies whether the other end is a stockpile or wheelbarrow. The nearest accessible target is selected when opening the menu and stays fixed until reopening; both ends must still be loaded, parked, in range and accessible on every click. No items pass through the player's pockets. A full destination leaves all remaining goods in the source.

Craft a Material Stockpile from **three planks across the top row and two sticks beneath the outer planks**. Place it normally and right-click its timber base to open cargo. Its original 64px/block pallet uses the wheelbarrow's timber/iron family; representative load visuals are bounded to 18 blocks per stockpile and 12 per wheelbarrow, independent of quantity. Cargo geometry is visual rather than a changing collision shape. Loaded stockpiles reject player breaking and resist explosions; loaded wheelbarrows cannot be recovered into portable items. Forced administrator replacement/removal is outside these ordinary custody protections.

Each store owns one saved balance. Native entity/block-entity saves retain counts separately from count-one item identities, including counts beyond 32-bit integers. Lowering a mass limit or changing material data never truncates existing contents: an overfull/unsupported saved load may be withdrawn, while new insertion is blocked. Mass caches invalidate on cargo/material changes; menu icons refresh on stock/page changes, and stockpile world updates coalesce once per tick. No per-frame inventory scans or one-entity-per-item simulation are added. The [manual-handling package](../development_plan.md#physical-storage-and-increasing-scale--active-package) still needs Survival wheelbarrow acquisition, loaded balance, supply-fed building and broader multiplayer/terrain review.
