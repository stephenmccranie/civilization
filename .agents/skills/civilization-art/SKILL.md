---
name: civilization-art
description: Develop Civilization mod artwork from a brief through generated mockups, autonomous visual refinement, native asset building and in-game review. Use for items, blocks, multiblocks, animated machines and shared UI art.
---

Use the project's [asset pipeline](../../../tools/modeling/README.md#complete-asset-pipeline). Commands and records support visual judgment; they do not replace it. Read the relevant shipped machine/item reference, the [approved visual direction](../../../design_direction.md#setting-and-material-style), and nearby existing art before designing.

For shaped/animated assets, read [native modeling practice](../../../tools/modeling/MODELING.md). Use measured assembly landmarks, fixed-camera neutral/textured reviews and checked texel density. The tested `studio.py` helpers support native batch construction and offscreen views; preserve editable projects and judge the actual model before publishing.

1. **Describe the asset first.** Create/fill its brief: purpose, recognizable silhouette, scale/bounds, materials, existing style references, ports/controls, construction pieces, moving parts/states, output types and gameplay invariants. Record role, technological stage, material behavior, signature feature and named neighboring assets in the brief. Raw substances need not display period ornament. Derive constraints from code and agreed design. Resolve routine art choices autonomously; ask only if a missing decision changes gameplay or scope.
2. **One coherent direction.** Generate one mockup with the built-in image-generation skill. Multiple competing designs are opt-in. Separate subject/shape, material and project-style reference roles. One image may serve several roles only when appropriate; an unrelated style reference must not dictate material texture. Pass actual inspected reference images, not just their filenames in prose. Minecraft/Blockbench geometry, Tesla-era materials and familiar readable controls are requirements. Mockup prompts can describe game texel density; high-resolution texture-master prompts must not request tiny 32×32 output. For item sprites, follow [native-size design guidance](../../../art/textures/sprite-design.md): use a clear silhouette, target-sized structural landmarks and readable material clusters instead of subpixel microtexture, then judge native-size exports before approving the source.
3. **Inspect, critique, iterate.** View the actual image. Check the pipeline's review criteria and record specific findings. Look for impossible crank/linkage axes, floating supports, wheel interference, inaccessible ports, implausible volume, incorrect part counts, perspective inconsistencies and invented mechanics. Check style against the named existing assets, not memory. Edit the chosen image with explicit invariants and targeted fixes. Do not generate independent faces or change the art direction to solve a small defect. Continue until remaining issues do not block implementation; never pass a flawed concept just because generation succeeded. If repeated edits plateau, simplify the design within scope and continue. Report an actual tool failure rather than silently accepting a defect. No routine user approval gate.
4. **Build the selected design.** Use Blockbench blockouts for shaped/animated assets, native Java models for static pieces, GeckoLib only for required animation, the existing sprite/family tools for raster exports, and shared cabinet parts for UI. Before texturing, extract a few visible landmarks and proportion targets from the selected mockup into the brief. Compare mockup and complete blockout at similar view/scale using the pipeline comparison tool: large masses, negative space, supports and characteristic fittings must survive translation. Correct a boxy silhouette with geometry, not texture noise. Include existing construction blocks with their actual materials; label unavailable pack materials as unverified. Multiblocks need individually identified pieces, guides/collision/ports and coherent textures. Do not silently preserve an old structural layout when it defeats the requested redesign; distinguish gameplay invariants from replaceable art/construction decisions.
5. **Textures and states.** Use one inspected material/master family and referenced edits, deliberate UVs and consistent pixel density. Put rivets/seams in textures instead of excessive geometry. Reference active-pack materials rather than copying Faithful. Active states may change local windows/emission, not the whole casing. Specify material-mark scale, direction, coverage and contrast for each texture family. Broad textured faces must not become blank plastic; avoid the opposite failure of noisy subpixel detail. Inspect native-sized item icons as well as zooms. Permit small deliberate final pixel-art corrections for edges, accents and material marks through the reproducible `pixels` spec; do not hand-edit runtime files or add random noise. Preserve source images, exact prompts/references and editable models.
6. **Review what was built.** Inspect actual model views, textures and animation poses; then use the relevant hidden Photon/Faithful Minecraft scene. Check front/back/sides, item/held appearance when relevant, contextual guides for multiblocks, stopped/startup/running states and screen readability. Check moving Sable placement only for assets claimed to work aboard vessels. Review a contact sheet or in-game lineup with the brief’s named neighboring assets. Explicitly judge material identity, membership in Civilization’s visual family, distinction from neighbors, scale, contrast, saturation and detail density. Do not equate a successful process exit, generated mockup or geometry counter with visual acceptance.
7. **Finish consistently.** Keep simple-item findings in one compact stage-keyed review file; machines retain detailed mechanical/assembly evidence. Record pass/revise findings with hashed evidence, publish validated exports, update affected runtime integration and authoritative docs, and report actual checks/limitations. A completed art task needs coherent implemented assets, not only an attractive mockup. When the user asks only for mockups or planning, stop at that requested stage and label it clearly.

Use the current asset brief and latest user direction for selections. Earlier mockups remain provenance; a request to restart means a fresh brief and generation, not an edit constrained by a superseded concept.
